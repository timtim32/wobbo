# Design: work-and-wait

## Context

- **Claude Code hooks:** the bridge's Claude Code adapter (`bridge/src/adapters/claude_code.ts`) maps hook events to protocol events:
  - `PreToolUse` becomes `tool_start {tool}`, whatever the tool;
  - `Notification` becomes the informational `notification {message, notification_type}`, which the app ignores for state.

  So `AskUserQuestion` (Claude asking the user in the terminal) and `ExitPlanMode` (plan approval) put the session in `working`. A permission prompt that Claude Code shows after the app's 20 s `PermissionRequest` window leaves the session in `working` too.
- **`SessionRegistry.apply_event`:** only `waiting` comes from pending requests (`add_request`), restoring `state_before_wait` when they are gone. `Protocol.EVENT_KINDS` lists the event kinds. Unknown kinds change nothing.
- **Clips:** they are generated by `godot/tools/build_monster_clips.gd`. Every clip gets every body track, with the defaults from `BODY_TRACKS` for tracks it does not set. So a discrete track such as `arm_r_think_shown` is reset in every other clip. Hidden alternate parts (`arm_r_think`) come from `<g id="part-…" style="display:none">` groups in `monster.svg`, exported by `godot/tools/export_monster.gd`.
- **Current `waiting` clip:** 2.4 s long, with one 12 px hop near the end and an arm gesture.
- **`Monster.play(clip)`:** calls `body_player.play(clip)` without a blend.
- **`AvatarMood`:** returns `{clip, motion}`, with `STATE_CLIPS[working] = working`.

## Goals / Non-Goals

**Goals:**
- Waiting for the user is detected from Claude Code without changing what the agent does.
- The protocol change is additive and agent-neutral: other adapters can send `input_wait` later.
- The props are drawn in the existing style and pipeline, so they are hue-safe and render like the rest.
- The work clip rotation is pure and tested.

**Non-Goals:**
- Inferring waiting from tool output or timing.
- Matching props to tools.

## Decisions

### D1. A new event kind `input_wait`
- **Protocol:** `PROTOCOL.md` gets the row `input_wait | the agent waits for the user in its own UI | reason, tool`. It is additive, so `v: 1` stays. An older app ignores the unknown kind, which is the old behaviour.
- **Adapter (`claude_code.ts`):**
  - `PreToolUse` with `tool_name` in `WAITS_FOR_USER = ["AskUserQuestion", "ExitPlanMode"]` becomes `input_wait {reason: "tool", tool}` instead of `tool_start`;
  - `Notification` with `notification_type` `permission_prompt` or `elicitation_dialog` becomes `input_wait {reason: notification_type}`;
  - other notifications stay `notification`.
- **Registry:** `input_wait` sets `waiting` (and `tool` when given), through the normal `last_ts` ordering. Pending requests are not involved. The next state event (`tool_end`, `tool_error`, `prompt`, `tool_start`, `turn_end`) moves the session on as usual. For example, after `AskUserQuestion` is answered, the `PostToolUse` → `tool_end` gives `thinking`.
- **Send home:** `input_wait` counts as use (it moves `last_ts` into `waiting`), so it brings an away buddy back (`send-home` D2). That is wanted: Claude asks the user something.

*Alternative:* keep `tool_start` and let the app treat certain tool names as waiting. Rejected: tool names are Claude Code specific, and the adapter is where agent specifics belong.

**Spike S2:** in a real Claude Code session, check:
- that `PreToolUse` for `AskUserQuestion` arrives before the question shows, and `PostToolUse` after the answer;
- that a permission prompt in the terminal sends a `Notification` with `notification_type: "permission_prompt"`.

**Fallback:** if `notification_type` is missing, match the notification message ("needs your permission"). If `AskUserQuestion` sends no `PostToolUse`, the next `prompt` or `tool_start` ends the waiting anyway.
- **Result S2, first part (task 1.4, 2026-11-23):** observed in this Claude Code session after the plugin update, from the app's state log.
  - `PreToolUse` for `AskUserQuestion` arrives as `input_wait` when the question appears, and `PostToolUse` arrives about 6 s later, right after the answer. The order is as expected.
  - Claude Code also fired a `PermissionRequest` for `AskUserQuestion`. The plugin mirrored it to the app as a permission request, which kept the session `waiting` for up to 20 s after the answer, until the request timed out.
  - Fix: asking tools (`WAITS_FOR_USER`) are no longer mirrored as app permission requests, just like the buddy's own tools. Plugin 0.1.3.
- **Result S2, second part (plugin 0.1.3, same session after the update):**
  - `AskUserQuestion` gave `waiting` (tool `AskUserQuestion`) at once, without an app permission request.
  - About 6 s later a Claude Code notification of a waiting type arrived as `input_wait` (no tool).
  - The session stayed `waiting` for the full 2.5 minutes until the user answered, then went to `thinking`.
  - Not tried by hand: a real terminal permission prompt in another session (`permission_prompt`). This session runs in auto mode, where no terminal permission prompts appear. The mapping is covered by the adapter test with Claude Code's sample `permission_prompt` notification.

### D2. The `waiting` clip: a continuous jump for attention
`waiting` is rewritten as a 1.2 s loop with two hops:
- **Body:** each hop rises about 40 px, with a clear squash before the jump and on landing.
- **Arms:** *both* arms go high up in the air and shake quickly above the head.
- **Eye:** the pupil is biased towards the viewer (`pupil_bias (0, 0.15)`), the ears flop on each hop, and the mouth is `open`.

The user asked for this during spike S2: the hop should draw more attention, and both arms should shake higher in the air. The hops stay lower and quicker than the big `happy` jump, so `waiting` reads as "hey, over here" and not as joy. The loop starts and ends on the ground, so there is no visible jump at the loop point.

### D3. Props as hidden parts in `monster.svg`
New hidden groups, each with a pivot:
- `prop_hammer`: a wooden handle with a grey head, in the right hand. It hangs on the `arm_r` bone, so it swings with the arm.
- `prop_wrench`: a grey wrench in the right hand, on `arm_r`.
- `prop_laptop`: a small open laptop in front of the belly, on `body`.
- `prop_papers`: a small stack of light paper sheets in front of the belly, on `body`.
- `prop_page`: one page that flips over the stack, on `body`, pivoting at the stack's spine.
- `arm_front_l` / `arm_front_r`: two arms bent in front of the body, in the style of `arm_r_think`, on `body`. Arms are drawn behind the body, so the laptop and papers clips hide the normal arms and show these instead. Each has its own rotation track, for typing and holding. They were added while drawing (task 2.1): the props alone could not show hands at the laptop or papers.

**Style:**
- flat shapes, no outlines;
- new colours: wood `#B07A43`, metal `#9AA3AD` / `#6C757F`, laptop body `#3A3F47` with a screen glow `#9FD3FF`, paper `#F4F1E6`;
- the props are not hue-shifted (the shader shifts only the skin greens).

They are drawn at the rest pose of the hand they belong to. The hammer and wrench include the fingers drawn over their handle. The laptop and papers are drawn in front of the front arms: you see the back of the lid, or the stack, with the forearms going behind it.

**Pipeline:** `export_monster.gd` exports them like `arm_r_think`. `monster.gd` `PARTS` and `monster.tscn` get the sprites. `build_monster_clips.gd` gets the discrete tracks `prop_hammer_shown`, `prop_wrench_shown`, `prop_laptop_shown`, `prop_papers_shown` and `prop_page_shown`, all `false` by default, plus a `prop_page_rot` track. Because every clip writes every track, a prop is hidden in every clip but its own.

**Spike S1:** show the four work clips and the new `waiting` side by side at real size in `monster_preview`, and let the user judge whether the props are recognisable, in style and well placed. **Fallback:** simplify the shape (a bigger hammer head, a thicker laptop) or drop a prop that does not read at 110 pt, after asking the user.
- **Result S1 (task 2.4, 2026-11-23, by hand in `work_preview.tscn`):** approved after three rounds of feedback.
  - **The hammer** first pointed back to the shoulder when the arm rose. It is now drawn upright with its pivot at the fist. The clip turns it 180° (`prop_hammer_rot`), so the handle extends the forearm, with the fist at its end and the head across it. The swing goes up over the shoulder and strikes down at the side.
  - **`waiting`** shows the arms in front of the body (`arm_l_z` / `arm_r_z` = 1) instead of behind it.
  - **The skin shader** rotated every saturated colour, which turned the wooden handle green on a teal buddy. It now only shifts hues within 45° of the drawn skin green (`skin_hue` 100°).
  - **The page flip** overshot with cubic interpolation, so `prop_page_scale` is linear.
  - The user then asked for transitions: taking and putting away each prop (design D7).

### D4. Four work clips
Each clip loops in about 1–1.6 s:
- **`work_hammer`:** the right arm raises the hammer and strikes down twice, with a small body dip on impact and a squint on the hit.
- **`work_laptop`:** the laptop is shown, both arms are bent forward with quick small finger taps (alternating small arm rotations), and the eye looks down.
- **`work_wrench`:** the right arm turns the wrench in short back-and-forth arcs, with a slight body lean.
- **`work_papers`:** the stack is shown, the left arm flips `prop_page` over (rotation 0 → π, then reset while hidden behind the stack), and the eye follows it.

The current `working` clip stays as the fifth variant. `Monster.LOOPING_CLIPS` gets the four new clips.

### D5. Rotating work clips in `AvatarMood`
`WORK_CLIPS = [working, work_hammer, work_laptop, work_wrench, work_papers]`.
- **Switching:** while the state is `working`, the mood keeps `_work_clip` and `_work_until`. When `now >= _work_until`, or when it enters `working`, it picks a random clip other than the current one with its seeded RNG, and sets `_work_until = now + rand(8000, 15000)`.
- **Clip changes:** no new code needed. The `BodyPlayer` in `monster.tscn` already has `playback_default_blend_time = 0.15`, so every clip change crossfades. This was found during task 2.3, and the planned 0.2 s blend in `Monster.play` was dropped. Discrete tracks such as visibility switch at the start of the blend.

### D7. Taking and putting away props
The user asked for this after spike S1. Each prop clip gets two one-shot clips, `<clip>_in` and `<clip>_out`, of about 0.6 s:
- **`work_hammer` / `work_wrench`:** the right arm swings inward, so the hand goes behind the body. While the hand is hidden, the prop's visibility switches. Then the arm swings out to the work pose (in), or the reverse (out).
- **`work_laptop`:** the front arms and the closed laptop appear. The lid opens by scaling the laptop up from its base (`prop_laptop_scale` y 0.12 → 1, pivot at the base). Out closes it, then the hanging arms return.
- **`work_papers`:** the stack and the page rise together from their bottom edge between the front arms (`prop_papers_scale`, `prop_page_scale`; both pivots at the bottom), like the laptop lid. `_in` is exactly `_out` played backwards, as the user asked. The first versions looked odd to the user: growing from the centre with the page popping in at the end, then the front arms showing before the stack rose.

**In `AvatarMood`:** a work clip has the phases `in` → loop → `out`.
- **Entering `working`:** plays `<clip>_in`, then the loop.
- **A switch:** plays `<old>_out`, then picks the next clip and plays its `_in`.
- **Leaving `working`:** plays the current `_out` first. Only then does the new state's clip or reaction follow, within the 1 s the spec allows.
- **Plain `working`:** it has no prop and no transitions.
- **Walking or travelling:** the work clip is dropped, and the walk clip hides all props.

### D6. Plugin update
- The plugin version goes to 0.1.2, and `bun run build:plugin` builds the binary.
- The user updates the plugin with `claude plugin marketplace update buddy-local` and `claude plugin update buddy-bridge@buddy-local`, then restarts the Claude Code sessions.
- The Claude Desktop configuration uses the same binary path and picks it up on its next start.
- The README documents the update.

## Risks / Trade-offs

- [`AskUserQuestion` is a Claude Code tool name that may change] → It lives in the adapter's list, so it is easy to adjust. Spike S2 checks today's names.
- [A blend between clips with different visible props shows a prop popping in or out] → Accepted: the switch happens at the start of the 0.2 s blend, and a prop appearing in the hand reads as grabbing it.
- [Found while trying it (the user saw three arms, or a hammer moving without an arm): a blended `play()` does not apply discrete keys at time 0 in Godot 4.7. The previous clip's visibility (arms, props, mouth) stayed in place] → `Monster.play` and `Monster.mirror` now set the new clip's discrete values themselves (`_apply_discrete`), and only motion crossfades. A regression test covers it.
- [Five extra props make the SVG and the atlas a little bigger] → Small parts, negligible.
- [Waiting detected from a `Notification` can come after the app's own permission request has already been withdrawn] → Intended: then Claude Code waits for the user in the terminal, and the buddy keeps jumping until the next step.
